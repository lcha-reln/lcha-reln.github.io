根据 高可用系统架构解决方案 中提出的方案，以下是生产环境中实际遇到（或极易触发）的五个典型问题。每个问题均按 故障现象 → 排查流程 → 根因分析 → 解决方案 → 延伸思考 的结构展开，可直接作为故障复盘模板使用。

1. GC 停顿导致 ZooKeeper Session 超时，引发无谓主从切换（假死问题）

故障现象

  • 监控告警：主节点在凌晨 2:17 突然失去 Leader 身份，从节点接管成为新 Leader
  • 但原主节点进程并未宕机，30 秒后恢复正常，变为 Follower
  • 业务侧反馈：凌晨有约 30 秒的交易中断，且切换后出现少量重复订单

排查流程

Step 1：确认切换是否真实发生

查看 ZooKeeper 审计日志，确认临时节点 /app/{group}/leader/latch-00001 在 2:17:03 被删除，说明 ZK 判定原主节点 session 已超时。

Step 2：排查原主节点为何”失联”

查看原主节点的 GC 日志，发现在 2:16:45 触发了一次 Full GC，STW（Stop-The-World）持续了约 22 秒：

ZK 的 sessionTimeout 配置为 30s，tickTime=2000，实际 ZK 服务端的 session 超时判定区间是 [2*tickTime, 20*tickTime] 即 [4s, 40s]。但 Curator 客户端的 sessionTimeoutMs=30000，22 秒的 STW 加上后续的 TCP 重传延迟，累计超过了 session 协商后的实际超时阈值，导致 session 过期。

Step 3：确认切换后的数据一致性

从节点接管后，检查 Redis 中的版本号：

  • 原主节点最后发布的 master_version_{group} offset = 58320
  • 从节点接管时自身已消费到 offset = 58318（落后 2 个批次）

从节点成为 Leader 后，从 offset 58318 继续消费，导致 58319、58320 的消息被重复处理。由于下游系统未做幂等，产生了重复订单。

根因分析

  1. 直接原因：Full GC STW 时间过长，导致 ZK session 超时，触发了不必要的 Leader 切换
  2. 间接原因：内存中大量长生命周期对象（如全量账户 HashMap）晋升到老年代，且未针对大内存堆做 GC 调优
  3. 衍生问题：下游消费端缺少幂等保护，切换后重复消费消息产生脏数据

解决方案

短期止血

  • 将 JVM 垃圾收集器从 G1 切换为 ZGC（JDK 17+），STW 控制在 10ms 以内
  • 调大 ZK sessionTimeout 至 40s，给 GC 留足容忍窗口（但不宜过大，否则真故障时 RTO 变长）

长期治本

  • 在 ClusterService.setLeader(false) 回调中增加”优雅降级”逻辑：检测到自己失去 Leader 后，不立即停止，而是先比对自身 offset 与 Redis 中版本号，如果差距在安全阈值内（如 < 5），延迟 5s 再停止处理，给 ZK 重连一个缓冲窗口
  • Kafka 下游消费端必须基于业务唯一键做幂等去重（如 orderId + tradeSeq）
  • 增加 GC 监控大盘，对 STW > 5s 的事件实时告警

延伸思考

Q：为什么不把 ZK sessionTimeout 设得很大，比如 5 分钟？

sessionTimeout 直接决定了真实故障场景下的 RTO。如果设为 5 分钟，主节点真的宕机时，从节点要等 5 分钟才能感知并接管，这对金融系统是不可接受的。

这是一个 “故障检测速度”与”误判容忍度” 之间的权衡，正确做法是优化 GC 减少 STW，而不是放大超时阈值来掩盖问题。

2. 主从指纹不一致，从节点触发停机告警

故障现象

  • 凌晨 3:00 从节点突然自动停机，日志中出现：
  • 主节点运行正常，业务未受影响
  • 但系统退化为单节点运行，失去高可用保障

排查流程

Step 1：确认指纹不一致的范围

查看从节点日志，发现从 offset 102450 开始指纹就已不一致，只是到 102456 才触发停机阈值（连续 N 次不一致）。

Step 2：对比主从的输出消息

在 offset 102450 处，主节点产生了 3 条输出消息，从节点产生了 2 条。少了一条关于”风控参数更新”的消息。

Step 3：排查消息差异的原因

回溯代码，发现在 offset 102450 对应的这批 Kafka 消息中，有一条是”动态配置变更”消息。

主节点在处理该消息时，触发了 Apollo 配置的热更新回调，更新了内存中的风控阈值参数。而从节点因为 Apollo 推送的时序差异，在处理同一条消息时，使用的仍是旧的风控阈值。

主节点处理顺序：

  1. 收到 Kafka 消息（offset=102450）
  2. Apollo 回调触发，风控阈值从 1000 → 500（恰好在此刻推送到达）
  3. 用新阈值 500 计算 → 触发风控拦截 → 产生一条风控告警输出消息

从节点处理顺序：

  1. 收到 Kafka 消息（offset=102450）
  2. Apollo 推送尚未到达，风控阈值仍为 1000
  3. 用旧阈值 1000 计算 → 未触发风控 → 没有风控告警输出消息

根因分析

主从节点的状态变更逻辑中，混入了外部非确定性输入（Apollo 配置推送的时序不一致），违反了 “相同输入 + 相同逻辑 = 相同输出” 的核心前提。

这个问题的本质是状态机的确定性被破坏。

在 Active-Active 架构中，主从节点独立计算，要求所有影响状态的输入都必须通过 Kafka 消息来传递，确保主从收到完全相同的输入序列。而 Apollo 配置推送是一个旁路输入，不经过 Kafka，天然无法保证主从的接收时序一致。

解决方案

核心原则：一切影响状态的输入，必须走 Kafka 消息通道。

  1. 配置变更不再由 Apollo 直接推送到计算引擎内存，而是：

  1. 对所有旁路输入做审计，包括：定时任务触发、HTTP 管理接口调用、数据库配置加载——凡是会影响计算结果的，全部改为通过 Kafka 消息驱动

  2. 增加”旁路输入检测”防护：在 Disruptor handler 之外的线程如果试图修改内存状态，直接抛异常拦截

延伸思考

Q：为什么不直接对全量内存状态做哈希来校验一致性，而是只对输出消息做指纹？

全量内存状态可能包含数十万甚至百万个对象（账户余额、订单簿、持仓信息等），每批次做一次全量哈希的开销是 O(N)，在高频处理场景下（如每秒数万批次）性能完全不可接受。

而输出消息是增量的，通常每批只有几条到几十条，计算 MD5 的开销是 O(1) 级别。基于”相同输入 + 相同确定性逻辑 = 相同输出”的前提，输出一致性可以等价推导出状态一致性。

当然，这个前提一旦被破坏（如本案例），指纹校验就会立即暴露问题，这恰恰是指纹机制的价值所在。

3. 快照恢复失败 + Kafka 消息过期，节点无法启动

故障现象

  • 某 Group 的主从节点同时宕机（所在物理机硬件故障）
  • 运维在新机器上重新部署后，节点启动失败，日志报错：

排查流程

Step 1：理解错误含义

  • 最新快照（offset=85600）文件损坏，CRC32 校验失败
  • 次新快照（offset=82100）文件完整，但 Kafka 中 offset=82100 的消息已过期被删除
  • Kafka 当前最早可用 offset=83000
  • 出现了 82100 到 83000 之间 900 条消息的数据空洞，无法回放

Step 2：排查最新快照为何损坏

查看快照写入日志，发现快照在写入过程中（写了约 70%），机器断电。写入未完成，文件被截断，CRC32 自然不匹配。

Step 3：排查为何次新快照的 offset 已过期

快照保留策略为：短期保留 6 份，每 5 分钟一份（覆盖 30 分钟）。但这台机器宕机后无人处理，直到 3 天后才在新机器上恢复。而 Kafka 的 retention.ms 配置为 7 天，但该 topic 的数据量很大，触发了 retention.bytes=1GB 的限制，导致早于 83000 的消息被提前清理。

故障时间线：

根因分析

  1. 快照文件损坏：写入过程中断电，未使用原子写入（先写临时文件，再 rename）
  2. Kafka 消息提前过期：只关注了 retention.ms（7 天），忽略了 retention.bytes（1GB）也会触发清理
  3. 运维响应不及时：3 天后才发现并处理，超出了快照与 Kafka 的安全重叠窗口

解决方案

紧急数据恢复

  • 从持久化层 MySQL 中导出 offset 82100 到 83000 之间的业务数据，手动构造补偿消息写入 Kafka
  • 或者直接基于 MySQL 数据重建内存状态（需要开发专门的全量重建工具）

快照写入原子化

写入流程改为：

  1. 写入临时文件 snapshot_{version}.tmp
  2. 计算 CRC32 并追加到文件尾部
  3. fsync 强制刷盘
  4. rename snapshot_{version}.tmp → snapshot_{version}.dat（原子操作）
  5. 更新 DB 元数据状态为 COMPLETED

恢复时只加载状态为 COMPLETED 的快照，.tmp 文件直接忽略。

Kafka 保留策略加固

如果必须限制大小，至少确保能覆盖所有快照版本之后的消息。

增加”快照健康度”监控

  • 定时检查：最新有效快照的 offset 与 Kafka earliest offset 的差距
  • 若差距小于安全阈值（如 < 2 小时的消息量），立即告警
  • 宕机超过 N 小时未恢复，自动触发备用恢复流程

延伸思考

Q：如果连 MySQL 的数据也不完整怎么办？

这属于灾难恢复（DR）范畴。在架构设计上需要增加 “长期归档快照” 机制——每天将一份快照上传到对象存储（如 S3/OSS），保留 30 天以上。即使本地快照和 Kafka 都丢失，仍可从归档快照恢复到某一天的状态，再从 MySQL 的 binlog 或审计日志追赶增量数据。当然，这种场景下 RTO 会退化到小时级甚至天级，但至少保证了 RPO（数据不丢失）。

4. Kafka 分区 Rebalance 风暴导致主从消费错乱

故障现象

  • 监控大盘显示：所有 Group 的消息处理延迟突然从 ms 级飙升到分钟级
  • 多个 Group 的从节点集中报出指纹不一致告警
  • Kafka Consumer 日志出现大量 Rebalance 记录：
  • 约 5 分钟后自行恢复，但期间有 2 个 Group 的从节点因指纹连续不一致而停机

排查流程

Step 1：确认 Rebalance 的触发原因

查看 Kafka Broker 日志，发现某运维人员在 14:30 对 Kafka 集群进行了滚动重启（升级 Broker 版本），导致部分 Partition 的 Leader 发生切换，引发 Consumer Group 的 Rebalance。

Step 2：分析 Rebalance 对主从的影响

Rebalance 期间，Consumer 被撤销（revoke）已分配的 Partition，然后重新分配。由于 enable-auto-commit=false，offset 由应用手动管理。但在 revoke 到 reassign 的间隔内：

  1. 主节点暂停消费约 30 秒
  2. 从节点的 Rebalance 可能比主节点更早或更晚完成
  3. 从节点先于主节点恢复消费，开始处理新消息，但 Redis 中的 master_version 仍停留在 Rebalance 前的值
  4. 从节点消费到某个 offset 时，发现自己已超过主节点版本 → 进入等待
  5. 但主节点 Rebalance 后被分配到了不同的 Partition（短暂错乱），处理了不同的消息 → 版本号推进了，但内容不同
  6. 从节点比对指纹 → 不一致 → 停机

Step 3：确认 Partition 分配是否稳定

发现 Kafka Consumer 使用的是默认的 RangeAssignor，在 Rebalance 时不保证分配的稳定性。加上主从是两个不同的 Consumer Group，各自独立 Rebalance，分配结果可能不一致。

根因分析

  1. Kafka Broker 滚动重启引发 Consumer Rebalance，这是预期行为
  2. 但每个 Group 的主从节点必须消费完全相同的 Partition，系统设计上通过手动指定 Partition（assign）而非自动订阅（subscribe）来保证——排查发现某次代码变更误将 assign 改为了 subscribe
  3. subscribe 模式下，Rebalance 可能导致主从被分配到不同 Partition，打破了”相同输入”的前提

解决方案

紧急修复

  • 回滚代码，将 Kafka Consumer 恢复为 assign 模式，手动指定 Partition
  • 重启已停机的从节点

根本方案

防御性措施

  • 在代码中增加启动检查：如果检测到 Consumer 使用的是 subscribe 模式，直接拒绝启动并报错
  • Kafka Broker 滚动重启前，通过 Kafka Admin API 做 Preferred Leader Election，提前将 Partition Leader 迁移到不重启的 Broker 上，减少影响面
  • 增加 Rebalance 事件的监控打点，一旦发生 Rebalance 立即告警

延伸思考

Q：既然用了 assign 模式手动分配 Partition，那如果 Kafka 新增了 Partition 怎么办？

在这种架构下，Partition 数量与 Group 数量是强绑定的——每个 Group 消费固定的 Partition。新增 Partition 意味着新增 Group（水平扩容），这是一个需要规划的运维操作，而不是自动感知的。如果确实需要动态扩缩容，应该在管控层面做编排：先创建新的 Group 主从节点，再将新 Partition assign 给它们，最后通过路由层（如 Gateway）将对应用户的流量切到新 Group。整个过程是受控的，而不是由 Kafka Rebalance 自动完成。

5. Redis 故障导致从节点版本锚点丢失，引发连锁雪崩

故障现象

  • 16:00 Redis 集群发生主从切换（Redis Sentinel 触发 failover）
  • 16:00-16:02 期间，所有 Group 的从节点日志报出：
  • 从节点因无法获取主节点版本号，全部进入”等待”状态，停止消费
  • 主节点不受影响，继续处理消息，版本号持续推进
  • 16:02 Redis 恢复，从节点读取到最新版本号，发现自己落后主节点 12000 个 offset
  • 从节点开始疯狂追赶，CPU 飙升到 100%
  • 追赶过程中，大量指纹校验请求打向 Redis → Redis 压力激增 → 部分请求超时 → 从节点又进入等待 → 反复震荡
  • 持续约 10 分钟后才逐渐稳定

排查流程

Step 1：确认 Redis 故障的影响面

Redis 用于三个关键场景：

  1. 主节点发布版本号 + 指纹（写）
  2. 从节点拉取版本号 + 指纹（读，每 10ms 一次）
  3. 从节点写入心跳（写，每秒一次）

Redis 切换期间，写入和读取全部失败。主节点的版本号无法发布，但主节点自身处理不受影响（版本号发布失败只影响从节点的追赶判断）。

Step 2：分析从节点追赶风暴

从节点 2 分钟未消费，积压了约 12000 条消息。恢复后的追赶逻辑是：

每批校验都要查 Redis，12000 条消息分成若干批次，短时间内产生大量 Redis 请求，加上其他 Group 的从节点同时追赶 → Redis 被打满。

根因分析

  1. Redis 作为关键依赖的单点风险：虽然用了 Redis Sentinel 做高可用，但 failover 期间（通常 10-30 秒）仍有不可用窗口
  2. 追赶模式缺少限流：从节点追赶时没有速率控制，所有 Group 同时追赶形成”惊群效应”
  3. 指纹校验策略过于严格：追赶过程中每批都校验指纹，放大了对 Redis 的依赖

解决方案

从节点追赶限流

版本号本地缓存 + 降级策略

Redis 连接池预热 + 哨兵感知优化

  • 使用 Lettuce 替代 Jedis，支持自动拓扑刷新，Redis failover 后能更快连接到新主节点
  • 配置 topology-refresh-period=5s，减少 failover 后的感知延迟

延伸思考

Q：如果 Redis 长时间不可用（比如超过 10 分钟），从节点应该怎么处理？

分两种情况：

  • 落后差距在安全范围内（如 < 5 分钟的消息量）：从节点可以继续消费但跳过指纹校验，依靠”相同输入 + 相同逻辑 = 相同输出”的确定性保证来维持一致性，Redis 恢复后再做一次指纹校验来验证
  • 落后差距过大或 Redis 超过阈值仍未恢复（如 15 分钟）：从节点应该主动停止消费并告警，因为此时它既无法校验一致性，也无法更新心跳（主节点会认为从节点已宕机）

这本质上是一个 可用性 vs 一致性 的权衡——短时间内可以牺牲校验来保可用，长时间则必须以一致性为先。
