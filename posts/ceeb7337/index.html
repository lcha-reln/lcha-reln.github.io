一、系统总览

1.1 资金划转在交易所中的定位

资金划转是交易所的核心基础设施之一，连接了现货账户、合约账户、杠杆账户、理财账户等多个子系统。它不涉及链上操作（区别于充值/提现），而是链下的账本变更，因此对一致性、实时性和并发性能要求极高。

2.3 面试问答

Q1：账户间划转为什么不需要走消息队列异步处理？

账户间划转是单用户的两个账户之间操作，涉及的行锁范围小（同一 user_id 的两行），事务轻量且快速。同步事务即可满足实时到账的体验需求。引入 MQ 反而增加了复杂度（最终一致性、补偿机制等），在这里得不偿失。但如果是批量划转场景，则适合用 MQ 解耦。

Q2：如果划转中间数据库宕机了，会不会出现一边扣了一边没加的情况？

不会。整个操作在一个本地数据库事务中完成（@Transactional），要么全部成功，要么全部回滚。但如果涉及跨库事务（如 from 和 to 在不同分库中），则需要引入分布式事务方案，如 TCC 或 Saga。

Q3：乐观锁和悲观锁在这里怎么选？

账户间划转的并发冲突概率低（用户自己操作自己的账户），乐观锁（available >= amount）足够。悲观锁（SELECT ... FOR UPDATE）会产生行锁等待，在高并发场景下性能不如乐观锁。但如果系统存在大量自动化策略同时操作同一账户，可以考虑悲观锁保证操作的线性化。

Q4：分库分表环境下，如果 from_account 和 to_account 不在同一个分片怎么办？

分片键通常是 user_id，账户间划转是同一用户，自然落在同一分片。如果是用户间划转，两个用户可能在不同分片，这时需要分布式事务（详见第四节）。

3.3 面试问答

Q1：子母账户划转涉及两个 user_id，如果分库分表怎么保证事务一致性？

这是个经典的分布式事务问题。常用方案有三种：

方案一：TCC（Try-Confirm-Cancel）

  • Try：冻结母账户金额，预增子账户（写入 pending 记录）
  • Confirm：扣减母账户冻结，确认子账户增加
  • Cancel：解冻母账户，删除 pending 记录

方案二：可靠消息最终一致性

  • 本地事务扣减母账户 + 写入消息表
  • 定时任务/binlog 监听投递消息
  • 消费者增加子账户（幂等消费）

方案三：转账中间账户

  • 引入平台中间账户，划转拆解为两步本地事务
  • 母 → 中间账户（事务 A）、中间账户 → 子（事务 B）
  • 中间账户不可为负，异常时定时任务补偿

实际生产中，方案二最常用，因为划转对实时性要求是”秒级”而非”毫秒级”。

Q2：批量划转如果中间有一笔失败了，整体怎么处理？是全部回滚还是部分成功？

批量划转采用部分成功策略（非原子）。每笔划转独立消费、独立事务，失败的笔记录 status=FAILED 和失败原因。客户端通过批次号查询每笔状态。原因如下：

  • 原子性回滚代价极高（已成功的笔需要逆向补偿）
  • 业务上每笔失败原因不同（余额不足 vs 子账户冻结），不应互相影响
  • 机构客户更倾向于知道”哪些成功、哪些失败”而非全部重来

Q3：子账户之间的划转（子 → 子）如何控制？

子 → 子划转通常需要母账户授权或母账户代为操作。实现上有两种模式：

  • 代理模式：母账户以自己的身份发起，指定 from_sub 和 to_sub，权限由母账户身份天然保证
  • 授权模式：子账户持有划转权限，通过 transfer_perm 和额外的子→子白名单控制

多数交易所采用代理模式，因为安全性更高。

Q4：如何防止母账户在批量划转时超额分发（race condition）？

预扣机制：

  1. 批量划转入口先一次性冻结总金额（原子操作）
  2. 每笔异步消费时从冻结金额中扣减
  3. 全部完成后，剩余冻结金额解冻

这样即使多个批次并发，冻结操作保证总额不超。

4.3 面试问答

Q1：用户间划转如何实现免手续费？和链上转账的本质区别是什么？

用户间划转是链下操作，本质上是平台内部账本的借贷记账（类似银行内部转账），不涉及区块链交易，因此：

  • 无 gas 费 / 矿工费
  • 不需要等待区块确认
  • 实时到账（毫秒级）
  • 平台可以选择免手续费来提升用户粘性

技术上，就是一次数据库事务中 A 减 B 加。平台的资产总量不变，只是用户间的数字调整。

Q2：收款方身份验证如果支持邮箱查询，如何避免被用来”撞库”？

多层防护：

  1. 限流：单 IP / 单用户对收款方查询接口做严格限流（如 10 次/分钟）
  2. 模糊返回：查询结果只返回脱敏信息（如 k***@gmail.com），不返回完整信息
  3. 行为风控：连续查询不同收款方触发风控拦截
  4. CAPTCHA：高频访问触发人机验证
  5. 审计日志：所有查询记录入库，便于事后追溯

Q3：2FA 验证和划转操作之间有时间窗口，如何防止 TOCTOU 攻击？

TOCTOU（Time of Check to Time of Use）是指验证和执行之间存在时间差的安全风险。防护方案：

  1. Token 化：2FA 验证通过后生成一个一次性 token（有效期 60s），划转时必须携带此 token
  2. Token 绑定请求参数：token 绑定具体的转账参数（收款人、金额、币种），篡改参数后 token 失效
  3. Token 单次消费：使用 Redis SETNX 保证 token 只能被消费一次

Q4：用户间转账的反洗钱（AML）通常怎么做？

交易所的 AML 系统通常包含以下环节：

  1. 规则引擎实时拦截：
    • 大额交易预警（超过阈值自动触发人工审核）
    • 频繁小额转账检测（”蚂蚁搬家”模式）
    • 新注册用户短时间大额转出
  2. 风控模型评分：基于用户历史行为、设备指纹、IP 地理位置等特征计算风险评分
  3. 黑名单/灰名单：OFAC 制裁名单匹配、历史违规用户标记
  4. 大额交易报告（CTR）：按照合规要求向监管机构报告
  5. 可疑活动报告（SAR）：异常行为触发上报流程

Q5：如果要支持用户间转账”到账前可撤回”的功能，你会怎么设计？

引入延时到账机制：

  1. 划转不立即执行，状态设为 PENDING，扣减发起方余额并冻结等额资金到一个中间状态
  2. 设置延时窗口（如 24 小时），窗口期内发起方可主动取消（解冻返还）
  3. 超时未取消，定时任务扫描到期的 PENDING 记录，执行实际到账（解冻并转给收款方）
  4. 收款方在 PENDING 期间可以看到”待入账”金额但不可使用

核心难点在于定时任务的可靠性（推荐使用延时消息 RocketMQ 或 Redis Sorted Set），以及与即时到账两种模式的灵活切换。

Q2：合约保证金的”可划转金额”计算在高频交易场景下，如何保证准确性？

这是一个经典的一致性问题。合约保证金受行情波动影响（浮动盈亏），每时每刻都在变化。

实时计算方案：

  • 划转前实时拉取当前 mark price，计算最新的仓位价值和维持保证金
  • 使用 SELECT ... FOR UPDATE 锁住账户行，防止划转和平仓并发

风控兜底方案：

  • 即使划转瞬间计算准确，划转后行情突变可能导致保证金不足
  • 解决：划转后的合约账户会被风控系统持续监控，低于强平线则触发强制平仓
  • 划转时预留安全垫（如可划转金额 = 实际可划转 × 0.95）

Q3：冻结资产有几种类型？它们的优先级关系是什么？

常见冻结类型：

冻结类型 触发场景 优先级
挂单冻结 用户下限价单 低
提现冻结 用户发起提现 中
风控冻结 风控系统触发 高
司法冻结 合规/法务要求 最高

优先级体现在解冻顺序上：低优先级的冻结可以被高优先级覆盖，但高优先级的冻结不会被低优先级操作解除。代码实现上，每笔冻结都有独立的冻结记录（freeze_record 表），frozen 字段是所有冻结记录的 sum，而非简单的单字段。

Q4：如果用 Redis 做预扣减（提升性能），怎么保证和 DB 的一致性？

Redis 预扣减是高频划转场景的性能优化方案，但必须解决一致性问题：

方案：

  1. Redis DECRBY 预扣减 available（原子操作，支持判断 >= 0）
  2. 预扣成功 → 发 MQ 消息 → 消费者写 DB（事务中同步 Redis 和 DB 的数据）
  3. 预扣失败 → 直接返回余额不足

一致性保障：

  • 消费者消费失败 → 重试 + 死信队列 + 人工兜底
  • Redis 宕机 → 从 DB 重建 Redis 数据（需要短暂停服或降级为 DB 直扣模式）
  • 定时对账任务：比对 Redis available 和 DB available，不一致则告警修复

关键：Redis 预扣减只是”乐观预扣”，最终以 DB 为准。这是 BASE 理论的实际应用。

6.3 面试问答

Q1：划转记录表如何做分库分表？查询时如何处理跨分片？

分片策略：按 user_id 分片（一致性哈希或取模）。

问题：用户 A 转给用户 B，记录写入 A 的分片。但 B 查询”收到的划转”时，需要在 B 的分片中能查到。

解决方案：

  1. 双写：一条划转记录写入两个分片——发起方分片和收款方分片（冗余存储）
  2. 宽表同步：划转成功后异步同步到 Elasticsearch，ES 不分片限制，支持任意维度查询
  3. 归档策略：热数据双写 MySQL，冷数据只存 ES/ClickHouse

多数交易所选择方案 2，因为划转记录是写少读多的场景。

Q2：导出百万级数据会遇到什么问题？怎么解决？

主要问题和解决方案：

问题 解决方案
内存溢出（OOM） SXSSFWorkbook 流式写入，控制 rowAccessWindowSize
查询慢 / DB 压力大 游标分页（LIMIT offset, batchSize），查从库
导出耗时长 异步任务 + 客户端轮询/WebSocket 通知
文件过大 分片导出（每 50 万行一个文件），打包成 ZIP
并发导出抢资源 限制同一用户同时只能有 N 个导出任务
offset 过大性能退化 改用 WHERE id > lastId LIMIT batchSize（游标翻页）

Q3：如何保证”划转状态”的准确性？如果异步处理卡住了，状态一直是”处理中”怎么办？

引入超时补偿机制：

  1. 划转记录写入时设置一个 expire_time（如 30 秒后）
  2. 定时任务每秒扫描超时的 PENDING/PROCESSING 记录
  3. 对超时记录执行检查：
    • 查询实际账户变动是否已经发生
    • 如果已经变动 → 更新状态为 SUCCESS
    • 如果未变动 → 尝试重试或标记为 FAILED 并补偿
  4. 发送告警通知运维人员

Q4：划转记录的时间筛选查询，如何避免大范围时间查询的慢查询？

  1. 强制时间范围限制：API 层限制查询跨度不超过 90 天
  2. 分区表：按月份做 RANGE 分区，查询时 MySQL 自动裁剪不相关分区
  3. 索引优化：确保时间字段在联合索引中的合适位置（通常放在高选择性字段之后）
  4. 冷热分离：超过 3 个月的数据查询走 ES/ClickHouse，不打 MySQL

Q1：请你设计一个完整的资金划转系统，从 0 到 1 你会怎么做？

第一阶段：核心模型设计

  • 设计统一账户模型（account 表），支持多账户类型
  • 设计划转流水表（transfer_record），支持幂等

第二阶段：核心能力建设

  • 实现同用户账户间划转（本地事务）
  • 实现跨用户划转（引入 TCC 或可靠消息）
  • 实现规则引擎（责任链模式，可插拔规则）
  • 实现 2FA 安全验证

第三阶段：进阶能力

  • 子母账户体系和权限控制
  • 批量划转（异步 MQ）
  • 对账系统（定时对账 + 实时对账）

第四阶段：运营 & 可观测性

  • 划转记录查询和导出
  • 监控告警（划转延迟、失败率、大额异常）
  • 运营后台（手动补偿、冻结解冻）

Q2：资金系统最怕什么？你会怎么保障资金安全？

资金系统最怕资损（少了钱）和超发（多了钱）。保障措施：

  1. 事务保障：单库事务 / 分布式事务（TCC / Saga / 可靠消息）
  2. 幂等设计：每笔划转有唯一 transfer_id，重复请求直接返回已有结果
  3. 乐观锁 / CAS：available >= amount 防止超额扣减
  4. 对账系统：
    • T+0 实时对账：每笔划转后检查借贷平衡
    • T+1 离线对账：每日汇总所有账户余额 vs 流水净额
  5. 资金日切：每日快照全量余额，便于追溯任意时间点
  6. 灰度发布：资金相关代码变更必须灰度，先放量 1% 用户观察
  7. 降级预案：异常时熔断划转入口，保护存量资金

Q3：如果线上出现了一笔划转”扣了钱但没加上”，你怎么排查？

这是一个典型的资金不平问题，排查步骤如下：

  1. 看流水：查 transfer_record 表，看这笔划转的状态。如果是 SUCCESS，说明 DB 层面两边都执行了
  2. 看账户：直接查 account 表的 available，看实际余额是否符合预期
  3. 看事务日志：如果用了分布式事务，查 TCC/Saga 的事务日志表，看是否有分支未执行
  4. 看 binlog：用 binlog 回放确认实际执行的 SQL
  5. 看缓存：如果用了 Redis 缓存余额，可能是缓存和 DB 不一致——对比 Redis 和 DB 的值
  6. 看消息队列：如果是异步模式，检查 MQ 消费是否有积压或消费失败
  7. 触发对账：手动触发对账任务，快速定位不平账户
  8. 应急处理：确认问题后，通过运营后台手动补偿（有审批流程）

Q4：账户间划转和用户间划转在技术实现上最大的区别是什么？

维度 账户间划转 用户间划转
事务范围 同一 user_id，本地事务 不同 user_id，可能跨分片
并发风险 低（自己操作自己） 高（多人同时转给同一人）
安全要求 低（已登录即可） 高（需要 2FA）
分布式事务 不需要 需要（TCC / 可靠消息）
风控要求 基本规则校验 AML + 限额 + 风控评分
通知 不需要 需要通知收款方

Q5：如何设计划转系统的监控告警？

监控分为业务指标和技术指标两个维度：

业务指标：

  • 划转成功率（目标 > 99.9%）
  • 大额划转实时告警（超过阈值立即通知风控）
  • 对账不平告警（T+0 实时对账发现异常立即告警）
  • 异常频率告警（某用户短时间内高频划转）

技术指标：

  • 划转接口 P99 延迟（目标 < 200ms）
  • 数据库事务超时比例
  • MQ 消费延迟和积压量
  • 死信队列数量（> 0 即告警）
  • Redis 和 DB 余额不一致数量

告警通道：即时通讯（飞书/钉钉）+ 短信 + 电话（按严重等级升级）。

Q6：你在实际工作中遇到过哪些资金相关的故障？怎么处理的？

（这是一道开放性问题，以下是一些典型案例供参考）

案例一：并发扣减导致余额为负

  • 原因：早期代码用 balance - amount 后直接 UPDATE，没有 WHERE available >= amount 的检查
  • 后果：用户余额出现负数
  • 修复：加乐观锁 + 全量扫描修复负余额账户 + 追溯资金去向

案例二：MQ 消费者宕机导致批量划转”丢消息”

  • 现象：100 笔批量划转只有 80 笔成功，20 笔状态一直是 PENDING
  • 原因：消费者 auto-commit offset 后宕机，消息实际未处理
  • 修复：改为手动 commit + 超时补偿任务扫描 + 幂等消费

案例三：对账发现平台总资产多了

  • 现象：T+1 对账发现某币种的用户余额总和 > 平台实际持有量
  • 原因：某次热钱包维护时，充值到账逻辑被重复执行（充值幂等键失效）
  • 修复：回滚多余入账 + 修复幂等逻辑 + 加强对账频率
