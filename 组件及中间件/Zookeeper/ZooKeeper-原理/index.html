ZooKeeper 为分布式应用提供高效且可靠的协调服务，采用 ZAB 协议保证数据一致性，广泛应用于 Dubbo、Kafka 等框架。

1. ZooKeeper 简介

1.1 ZooKeeper 是什么

ZooKeeper 是 Apache 的顶级项目。ZooKeeper 为分布式应用提供了高效且可靠的分布式协调服务，提供了诸如统一命名服务、配置管理和分布式锁等分布式的基础服务。在解决分布式数据一致性方面，ZooKeeper 并没有直接采用 Paxos 算法，而是采用了名为 ZAB 的一致性协议。

ZooKeeper 主要用来解决分布式集群中应用系统的一致性问题，它能提供基于类似于文件系统的目录节点树方式的数据存储。但是 ZooKeeper 并不是用来专门存储数据的，它的作用主要是用来维护和监控存储数据的状态变化，通过监控这些数据状态的变化，从而可以达到基于数据的集群管理。

ZooKeeper 官方支持 Java 和 C 的 Client API，社区也为 .NET、Python 等大多数语言提供了非官方 API。

1.2 应用场景

场景 说明
配置管理 集群节点通过中心源获取启动配置，更简单的部署
分布式集群管理 节点加入/离开，节点的实时状态监控
命名服务 类似 DNS，全局唯一命名
分布式同步 锁、栅栏、队列
Leader 选举 分布式系统的主节点选举
数据注册 中心化和高可靠的数据注册

1.3 ZooKeeper 的特性

特性 说明
顺序一致性 从一个客户端发起的事务请求，最终都会严格按照其发起顺序被应用到 ZooKeeper 中
原子性 所有事务请求的处理结果在整个集群中所有机器上要么都成功应用，要么都没有应用
单一视图 无论客户端连接的是哪个 ZooKeeper 服务器，其看到的服务端数据模型都是一致的
高性能 数据全量存储在内存中，读多写少场景下性能很高；写操作频繁时性能会大幅下滑
高可用 基于副本机制实现，支持故障恢复和 Leader 重新选举

1.4 设计目标

  • 简单的数据模型：树形结构的文件系统，树中的节点称为 znode
  • 可以构建集群：支持集群模式，一主多从架构，适合读多写少场景
  • 顺序访问：对每个更新请求分配全局唯一的递增 ID（zxid）
  • 高性能、高可用：数据全量存储在内存中，通过服务集群实现高可用

2. 核心概念

2.1 服务

ZooKeeper 服务是一个基于主从复制的高可用集群，集群中每个节点都存储了一份数据副本（内存中）。客户端只会连接一个 ZooKeeper 服务器节点，并维持 TCP 连接。

2.2 数据模型（znode）

ZooKeeper 的数据模型是一个树形结构的文件系统，树中的节点被称为 znode，根节点为 /。

  • 每个节点上都保存自己的数据和节点信息
  • znode 存储数据的大小被限制在 1MB 以内
  • znode 节点路径必须是绝对路径
  • 数据访问具有原子性：读写操作要么全部成功，要么全部失败

znode 的两种类型：

类型 说明
临时节点（EPHEMERAL） 客户端会话结束时自动删除，不允许有子节点
持久节点（PERSISTENT） 除非客户端主动执行删除操作，否则不会被删除

顺序标志（SEQUENTIAL）：创建 znode 时设置了顺序标志，ZooKeeper 会使用计数器为 znode 添加单调递增的数值（zxid），实现严格的顺序访问控制。

2.3 节点状态（Stat）

每个 znode 节点在存储数据的同时，都会维护一个 Stat 数据结构：

状态属性 说明
czxid 数据节点创建时的事务 ID
ctime 数据节点创建时的时间
mzxid 数据节点最后一次更新时的事务 ID
mtime 数据节点最后一次更新时的时间
pzxid 数据节点的子节点最后一次被修改时的事务 ID
cversion 子节点的更改次数
version 节点数据的更改次数
aversion 节点的 ACL 的更改次数
ephemeralOwner 临时节点时为创建该节点的会话 SessionID；持久节点时为 0
dataLength 数据内容的长度
numChildren 数据节点当前的子节点个数

2.4 集群角色

角色 职责
Leader 负责发起并维护与各 Follower 及 Observer 间的心跳；所有写操作必须通过 Leader 完成，再广播给其他服务器；同一时间只有一个 Leader
Follower 响应 Leader 的心跳；可直接处理并返回客户端读请求；将写请求转发给 Leader，并负责在 Leader 处理写请求时对请求进行投票
Observer 角色与 Follower 类似，但无投票权，用于扩展读性能

客户端可以从任意 ZooKeeper 服务器节点读取数据，但只能通过 Leader 服务写数据，且需要半数以上 Follower 的 ACK 才算写入成功。

2.5 ACL

ZooKeeper 采用 ACL（Access Control Lists）策略进行权限控制，每个 znode 创建时都会带有一个 ACL 列表。

认证方式：

方式 说明
digest 用户名和密码
sasl 通过 Kerberos
ip 通过 IP 地址

五种权限：

权限 说明
CREATE 允许创建子节点
READ 允许从节点获取数据并列出其子节点
WRITE 允许为节点设置数据
DELETE 允许删除子节点
ADMIN 允许为节点设置权限

3. 工作原理

3.1 读操作

Leader/Follower/Observer 都可直接处理读请求，从本地内存中读取数据并返回给客户端。

由于处理读请求不需要服务器之间的交互，Follower/Observer 越多，整体系统的读吞吐量越大。

3.2 写操作

所有写请求实际上都要交给 Leader 处理。

写 Leader 流程（5步）：

  • Leader 不需要得到 Observer 的 ACK（Observer 无投票权）
  • Leader 只需收到过半 Follower 的 ACK 即可，Leader 本身对自己有一个默认 ACK
  • Observer 虽无投票权，但仍须同步 Leader 数据

写 Follower/Observer 流程：

Follower/Observer 均可接受写请求，但不能直接处理，需要将写请求转发给 Leader。除了多了一步请求转发，其他流程与直接写 Leader 无任何区别。

3.3 事务

为了保证事务的顺序一致性，ZooKeeper 采用了递增的事务 id 号（zxid）来标识事务。

  • Leader 为每一个 Follower 服务器分配一个单独的队列，将事务 Proposal 依次放入队列中，按 FIFO 策略发送
  • Follower 收到 Proposal 后，以事务日志形式写入本地磁盘，写入成功后反馈 Ack
  • Leader 收到超过半数 Follower 的 Ack 后，广播 Commit 消息

zxid 结构： 64 位数字

  • 高 32 位：epoch，标识 Leader 关系，每次选出新 Leader，epoch 加一
  • 低 32 位：epoch 内的递增计数器

3.4 观察（Watch）

ZooKeeper 允许客户端监听它关心的 znode，当 znode 状态发生变化时，ZooKeeper 服务会通知客户端。

ZooKeeper 选择服务端主动推送状态（Watch 机制），而非客户端轮询。

Watch 机制特点：

  • 监听器实时触发
  • 监听器总是有序的
  • ZooKeeper 的 Watch 是一次性的，触发后立即销毁，需要重新注册

3.5 会话（Session）

ZooKeeper 客户端通过 TCP 长连接连接到 ZooKeeper 服务集群。会话从第一次连接开始建立，通过心跳检测机制保持有效状态。

连接流程：

  • 客户端启动时遍历配置的服务器列表，逐个尝试建立连接
  • 一旦建立连接，服务端为客户端创建一个新的会话
  • 超时时间内没有收到请求，则相应会话被视为过期，任何与该会话相关的临时 znode 都会被删除

会话的四个属性：

属性 说明
sessionID 全局唯一的会话标识
TimeOut 会话超时时间，客户端配置后由服务端最终确定
TickTime 下次会话超时时间点，用于”分桶策略”管理
isClosing 标记会话是否已关闭

Zookeeper 的会话管理主要通过 SessionTracker 负责，采用分桶策略（将类似的会话放在同一区块中进行管理）进行管理。

4. ZAB 协议

ZooKeeper 并没有直接采用 Paxos 算法，而是采用了名为 ZAB 的一致性协议。ZAB 协议是 ZooKeeper 专门设计的一种支持崩溃恢复的原子广播协议，是 ZooKeeper 数据一致性和高可用的解决方案。

ZAB 协议定义了两个可以无限循环的流程：

  • 选举 Leader：用于故障恢复，保证高可用
  • 原子广播：用于主从同步，保证数据一致性

4.1 选举 Leader

ZooKeeper 的故障恢复：

  • Follower 节点挂了：只要集群中有半数机器能够正常工作，整个集群就可以正常提供服务
  • Leader 节点挂了：需要通过 ZAB 协议的选举 Leader 机制进行故障恢复

关键术语

术语 说明
myid 每个 ZooKeeper 服务器在数据文件夹下创建 myid 文件，包含整个集群唯一的 ID（整数）
zxid 用于标识一次更新操作的 Proposal ID，高 32 位为 epoch（每次选出新 Leader 加一），低 32 位为该 epoch 内的序号

服务器状态

状态 说明
LOOKING 不确定 Leader 状态，认为当前集群中没有 Leader，会发起 Leader 选举
FOLLOWING 跟随者状态，知道 Leader 是谁
LEADING 领导者状态，维护与 Follower 间的心跳
OBSERVING 观察者状态，不参与选举，也不参与集群写操作的投票

选票数据结构

字段 说明
logicClock 自增整数，表示这是该服务器发起的第多少轮投票
state 当前服务器的状态
self_id 当前服务器的 myid
self_zxid 当前服务器上保存的数据的最大 zxid
vote_id 被推举的服务器的 myid
vote_zxid 被推举的服务器上保存的数据的最大 zxid

投票流程

  1. 自增选举轮次：每个服务器开始新一轮投票时，先对 logicClock 进行自增
  2. 初始化选票：清空投票箱，广播把票投给自己
  3. 发送初始化选票：每个服务器最开始都是广播把票投给自己
  4. 接收外部投票：尝试从其他服务器获取投票，记入投票箱
  5. 判断选举轮次：根据 logicClock 进行处理：
    • 外部 logicClock 大于自己：清空投票箱，更新 logicClock，重新对比并广播
    • 外部 logicClock 小于自己：直接忽略
    • 外部 logicClock 等于自己：进行选票 PK
  6. 选票 PK：基于 (self_id, self_zxid) 与 (vote_id, vote_zxid) 的对比，优先比较 vote_zxid，再比较 vote_myid，取更大值
  7. 统计选票：过半服务器认可了自己的投票，则终止投票
  8. 更新服务器状态：过半票投给自己则变为 LEADING，否则变为 FOLLOWING

ZooKeeper 集群节点数必须是奇数，且存活的节点数目不得少于 N + 1（N 为可容忍故障节点数）。

4.2 原子广播（Atomic Broadcast）

ZAB 协议的原子广播要求：

所有的写请求都会被转发给 Leader，Leader 会以原子广播的方式通知 Follower。当半数以上的 Follower 已经更新状态持久化后，Leader 才会提交这个更新，然后客户端才会收到一个更新成功的响应。

这类似于数据库中的两阶段提交协议。Leader 为每个事务请求生成对应的 Proposal，分配全局唯一的递增 ZXID，之后进行广播。

5. ZooKeeper 应用

5.1 命名服务

通过顺序节点的特性来生成全局唯一 ID，为分布式系统提供命名服务。

5.2 配置管理

利用 ZooKeeper 的观察机制，作为高可用的配置存储器，允许分布式应用的参与者检索和更新配置文件。

5.3 分布式锁

通过临时节点和 Watcher 机制实现分布式排它锁：

  1. 访问 /lock，创建带序列号的临时节点（EPHEMERAL + SEQUENTIAL）
  2. 每个节点尝试获取锁时，拿到 /locks 下的所有子节点，判断自己创建的节点是否是序列号最小的
    • 是最小的：成功获取到锁，执行完操作后删除节点（释放锁）
    • 不是最小的：监听比自己序列号小 1 的节点变化
  3. 被监听的节点删除后，下一个节点发现自己是最小节点，获取到锁

5.4 集群管理

  • 通过创建临时节点建立心跳检测机制，服务节点宕机时临时节点被删除，触发监听事件
  • 服务节点将自己的状态写入临时节点，完成状态报告或进度汇报
  • 通过数据的订阅和发布功能，对分布式系统进行模块解耦和任务调度
  • 通过监听机制，实现服务节点动态上下线，动态扩容

5.5 选举 Leader 节点

让所有服务节点去竞争性地创建同一个 ZNode，由于 ZooKeeper 不能有路径相同的 ZNode，必然只有一个服务节点能够创建成功，该服务节点成为 Master 节点。

5.6 队列管理

ZooKeeper 可以处理两种类型的队列：

  1. 同步队列：队列所有成员都聚齐时才可用，否则一直等待
  2. FIFO 队列：按照 FIFO 方式进行入队和出队操作，实现生产者和消费者模型

6. ZooKeeper 的缺点

ZooKeeper 的监听是一次性的，触发后立即失效。

6.1 不是为高可用性设计的

  • ZooKeeper 集群只能有一个 Leader，一旦机房之间连接出现故障，只有 Leader 所在的机房可以正常工作，其他机房只能停摆
  • 机房网段隔离调整时，ZooKeeper 将处于不可用状态
  • ZooKeeper 对网络隔离极度敏感，导致不可用时间比较多

6.2 选举过程速度很慢

ZooKeeper 的选举流程通常耗时 30 到 120 秒，期间 ZooKeeper 由于没有 Leader 都是不可用的。对于偶尔出现的半秒到一秒的网络隔离，ZooKeeper 会把不可用时间放大几十倍。

6.3 性能是有限的

典型的 ZooKeeper 的 TPS 大概是一万多，无法支撑每天动辄几十亿次的调用。因此 ZooKeeper 的 client 必须自己缓存业务系统信息，这导致 ZooKeeper 提供的”强一致性”实际上是做不到的。

6.4 无法进行有效的权限控制

ZooKeeper 的权限控制非常弱，在大型复杂系统中需要额外开发一套权限控制系统，增加了系统复杂性和维护成本，同时降低了总体性能。

6.5 难以避免业务系统的数据不一致

由于性能限制，无法让每次调用都走 ZooKeeper，业务系统总会存在两份数据（client 缓存的业务信息是定时从 ZooKeeper 更新的）。要保持数据的强一致性，唯一方法是”先 kill 掉当前 Leader，再在 ZooKeeper 上更新 Leader 信息”，但这需要人工介入，无法自动保障。
