分布式序列号机制深度解析

在高性能分布式系统中，消息的可靠有序传输是系统正确性的基础保障。序列号机制（Sequence Mechanism）是检测消息重复、缺失与乱序的核心技术手段，广泛应用于 HFT（高频交易）、高性能消息中间件、金融行情分发、可靠文件传输等领域。即便底层传输层（如 Aeron）本身具备一定的可靠性保障，应用层序列号仍是不可省略的防御层。

一、问题背景

分布式通信系统在运行过程中，消息传递可能发生以下三类异常：

  • 重复消息（Duplicate）：同一条消息被发送或投递多次，通常由重传机制、网络分区恢复或发送端故障重启引发
  • 消息缺失（Gap）：部分消息在传输过程中丢失，接收端未能收到连续的消息序列
  • 乱序消息（Out-of-Order）：消息到达顺序与发送顺序不一致，多路复用、网络多路径路由、重传机制均可导致乱序

上述三类异常若不加处理，将直接影响业务数据的完整性和一致性。序列号机制以极低的实现代价，提供了对三类异常的统一检测能力。

在实践中，序列号机制通常与单线程 + 分片（Shard）模型配合使用：每个 Shard 维护独立的序列号空间，单线程处理该 Shard 的消息流，消除序列号检查的并发竞争问题。

Gap 的大小为 sequence - lastSequence - 1，可精确计算缺失的消息数量及其序列号范围 [lastSequence+1, sequence-1]。

3.3 乱序消息检测（Out-of-Order Detection）

重要：Gap 检测与乱序检测在单纯比较 sequence 与 lastSequence 的实现中是同一个代码路径（sequence <= lastSequence 分支），接收端无法在收到乱序帧的瞬间区分”真正的乱序”与”Gap 后的补包”，需要结合上层恢复状态机判断。

3.4 重复消息检测（Duplicate Detection）

重复消息的检测代价极低——仅一次整数比较。对于幂等性要求严格的场景，需在 handleUnexpectedMessageAt 中进一步区分”已处理的重复帧”与”来自历史重传的旧帧”，可通过维护一个有界的已处理序列号窗口（sliding window）实现精确去重。

四、在 Aeron 中的应用

4.1 Aeron 流位置（Position）与应用层序列号的关系

Aeron 内部通过 流位置（Stream Position） 标识每个字节在 Log Buffer 中的绝对偏移量，Subscriber 可通过 Image.position() 读取当前消费位置。在同一 channel 和 stream 内，流位置单调递增，可在无故障的正常运行场景下替代应用层序列号进行连续性检测。

然而，流位置在以下场景中失效：

场景 流位置的限制
发布端进程重启 新 Publication 的 session ID 变化，流位置从 0 重新开始
Media Driver 重启 所有 Publication 的 Log Buffer 重置
接收端重连 Image 销毁重建，历史位置信息丢失
跨 channel/stream 关联 流位置仅在单一 stream 内有意义，无法跨流比较

Aeron 团队的明确建议：在 Aeron channel 和 stream 内使用应用层自定义的序列号和 Gap 检测机制，而非仅依赖流位置。原因是应用层序列号可跨进程重启持久化，提供更完整的故障恢复语义。

4.2 Aeron 中的序列号分层架构

应用层序列号嵌入消息 payload 的头部，与 Aeron 的帧头（Frame Header）相互独立，两层机制各司其职：Aeron 负责传输层的可靠投递，应用层序列号负责业务语义的完整性验证。

4.3 流位置 vs 应用层序列号

维度 应用层序列号 Aeron 流位置
跨进程重启持久性 可持久化，重启后连续 随进程重启归零
跨 session 连续性 支持 不支持（session 切换后位置断开）
故障恢复语义 完整，可重放任意 Gap 范围 受限于 Log Buffer 的 term 滚动窗口
业务语义定制 可自定义粒度（消息级、批次级） 固定为字节偏移
实现代价 每条消息额外 8 字节头 + 一次比较 零额外成本
适用场景 所有场景，尤其是需要故障恢复的场景 单进程、无故障场景的快速验证

七、实现要点总结

发送端约束：

  1. 序列号从固定起始值（通常为 1，或从持久化恢复）开始，严格单调递增
  2. 重传消息必须使用原始序列号，不得重新分配
  3. 序列号生成与消息发送必须在同一线程（或通过适当的同步机制保证有序性），防止序列号与消息的错位绑定
  4. 进程重启后，新序列号必须大于已持久化的最大已发送序列号，防止序列号回绕被接收端误判为重复

接收端约束：

  1. lastSequence 的更新必须在消息被成功处理之后进行，防止处理失败后序列号已推进导致消息永久丢失
  2. Gap 的处理策略需根据业务语义明确定义：是等待恢复、触发重传请求，还是直接跳过并告警
  3. 在允许乱序到达的场景（如多路并行传输），需引入接收窗口（Receive Window）暂存乱序帧，而非直接触发 Gap 处理
  4. lastSequence 应定期持久化，支持接收端重启后的 Gap 检测连续性
