## 二、现货交易

### 2.1 什么是现货交易

现货交易是"一手交钱、一手交货"的交易方式。以 ETH/USDT 为例：用 USDT 买入 ETH，成交后 ETH 真实到账，可以随时提现到链上自托管钱包。

**核心特征：**

| 特征 | 说明 |
|------|------|
| 即时结算 | 成交后资产立即到账，T+0 |
| 真实所有权 | 持有的币可以提现到链上钱包，完全自主 |
| 风险有限 | 最大损失为本金归零，不会产生负债 |
| 无利息成本 | 不涉及借贷，无持仓利息 |

## 三、杠杆交易

### 3.1 本质

杠杆交易是**现货交易的资金增强版**：用户向交易所借入资金，以更大的名义仓位参与现货市场，收益和亏损同步放大。

**5 倍杠杆做多 BTC 示例：**

```
第一步：用户本金 1000 USDT，5 倍杠杆
第二步：向交易所借入 4000 USDT，总购买力 5000 USDT
第三步：在现货市场买入 BTC（开仓价 50000 USDT/BTC，买入 0.1 BTC）
第四步：持仓期间，风控系统实时监控维持保证金率

维持保证金率 = (账户权益 / 借款金额) × 100%
预警线：< 130%
强平线：< 110%
```

**盈亏对比：**

| 情况 | BTC 价格变动 | 结果 |
|------|------------|------|
| 盈利平仓 | 涨至 55000（+10%） | 卖出 0.1 BTC = 5500 USDT，还款 4000 + 利息 10 USDT，净赚约 490 USDT，收益率 **49%** |
| 触发强平 | 跌至 45000（-10%） | 维持保证金率触及 112.5%，系统强制卖出，还款后剩余约 490 USDT，**亏损 51%** |

> 相比持有相同本金的现货交易，±10% 的价格变动在 5 倍杠杆下放大为 ±50%。杠杆是双刃剑，跌幅超过 `1/杠杆倍数` 即触发爆仓。

### 3.2 杠杆与现货的核心区别

| 对比项 | 现货交易 | 杠杆交易 |
|--------|---------|---------|
| 资金来源 | 全部自有 | 自有 + 借贷 |
| 资产所有权 | 完全拥有，随时提现 | 拥有，但还款前不能提现 |
| 利息成本 | 无 | 有，日利率约 0.02%~0.05% |
| 爆仓风险 | 无 | 有 |
| 收益 / 风险 | 线性 1 倍 | 线性 × 杠杆倍数 |

## 四、合约交易

合约交易与现货有根本区别：**你持有的不是真实的币，而是一份价格协议**。整个过程不涉及实物交割，只结算开平仓之间的盈亏差价。

### 4.1 U 本位合约

以 USDT 作为保证金和结算货币，是目前最主流的合约类型，占全市场合约交易量的 80% 以上。

**示例（10 倍杠杆做多 BTC/USDT 永续）：**

```
开仓：保证金 1000 USDT，10 倍杠杆，合约名义价值 10000 USDT
      开仓价格 40000 USDT/BTC

场景 A：BTC 涨至 44000 USDT（+10%）
  盈利 = 10000 × 10% = 1000 USDT
  总资产 = 2000 USDT，收益率 100%

场景 B：BTC 跌至 36000 USDT（-10%）
  亏损 = 10000 × 10% = -1000 USDT
  保证金归零，触发强制平仓（爆仓）
```

**优点：** 盈亏以 USDT 计价，逻辑直观；保证金价值不受标的币波动影响。

### 4.2 币本位合约

以标的币（如 BTC、ETH）作为保证金和结算货币。

**示例（10 倍杠杆做多 BTC/USD 永续）：**

```
开仓：保证金 1 BTC，10 倍杠杆，BTC 价格 40000 USDT
      风险敞口 = 10 BTC

场景 A：BTC 涨至 44000 USDT（+10%）
  合约盈利 = 10 × (44000-40000)/40000 = 1 BTC
  总资产 = 2 BTC，折合 88000 USDT（+120%，双重收益）

场景 B：BTC 跌至 36000 USDT（-10%）
  合约亏损 = -1 BTC
  总资产 = 0 BTC，保证金归零（双重亏损）
```

> 币本位合约存在"双刃剑效应"：BTC 上涨时盈利同时以更贵的 BTC 计价，收益放大明显；但下跌时合约亏损叠加保证金缩水，风险也翻倍。适合长期看多、以 BTC 为记账单位的用户，不适合短线投机。

### 4.3 U 本位 vs 币本位

| 对比维度 | U 本位合约 | 币本位合约 |
|---------|---------|---------|
| 保证金 | USDT（稳定） | BTC / ETH（波动） |
| 盈亏计价 | USDT，直观 | 标的币，有双向放大效应 |
| 适合人群 | 短线投机、日内交易 | 长期囤币、以币计价 |
| 市场占比 | >80% | <20% |

### 4.4 永续合约

永续合约是目前交易量最大的合约类型（占比 90%+ ），其核心特征是**没有到期日**，可以无限期持仓。

**资金费率机制（防止合约价格与现货长期偏离）：**

```
合约价 > 现货价（市场整体看涨）
  → 资金费率为正（如 +0.01%）
  → 多头每 8 小时向空头支付费用
  → 做多成本增加，多头平仓，合约价格回落

合约价 < 现货价（市场整体看跌）
  → 资金费率为负（如 -0.01%）
  → 空头每 8 小时向多头支付费用
  → 做空成本增加，空头平仓，合约价格上涨
```

资金费率**每 8 小时结算一次**（通常为 UTC 00:00、08:00、16:00），大多数交易所（如 Binance、OKX）的基础费率锚定在 ±0.01%。

**持仓成本测算：**

> 持有 10000 USDT 的 BTC 永续多单，资金费率 +0.01%：
> - 每 8 小时支付：10000 × 0.01% = 1 USDT
> - 每天支付：3 USDT
> - 行情极度偏多时费率可升至 +0.1%，每天成本 30 USDT

长期持有永续合约时，资金费率累积成本不可忽视。

### 4.5 交割合约

交割合约有固定到期日（如 `BTCUSDT-1229` 代表 12 月 29 日到期），到期后按**交割价格**（通常为最后 1 小时现货均价）强制现金结算，仓位自动清零。

**典型应用场景：**

**① 矿工套期保值**

```
某矿场预计 12 月产出 10 BTC，当前 BTC 价格 40000 USDT
担心价格下跌，在 12 月交割合约开 10 BTC 空单

结果：
  BTC 跌至 35000 → 现货亏 50000 USDT，合约盈 50000 USDT，净盈亏 = 0
  BTC 涨至 45000 → 现货盈 50000 USDT，合约亏 50000 USDT，净盈亏 = 0

效果：提前锁定 40000 USDT/BTC 的卖出价格，无论市场如何波动
```

**② 跨期套利（基差交易）**

```
发现：BTC 现货 40000 USDT，12 月交割合约 41000 USDT（溢价 2.5%）
理论上：接近交割日，合约价格会收敛至现货价

操作：买入 1 BTC 现货 + 卖出 1 张交割合约
到期结算：无论 BTC 涨跌，锁定 1000 USDT 的基差收益
```

### 4.6 永续 vs 交割

| 对比维度 | 永续合约 | 交割合约 |
|---------|---------|---------|
| 到期日 | 无，可无限持有 | 有，到期强制结算 |
| 价格锚定 | 资金费率（多空互付） | 到期自然收敛现货 |
| 持仓成本 | 资金费率，长期持仓需关注 | 无资金费，但有基差 |
| 流动性 | 极高 | 较低，越临近到期越活跃 |
| 适用人群 | 短线投机、日内交易 | 套保、跨期套利 |
| 市场占比 | >90% | <10% |

### 4.7 合约类型全览

| 合约类型 | 保证金 | 到期日 | 典型合约名 | 适用人群 | 市场占比 |
|---------|--------|-------|----------|---------|---------|
| U 本位永续 | USDT | 无 | BTCUSDT-PERP | 短线投机 | ~70% |
| U 本位交割 | USDT | 有 | BTCUSDT-1229 | 套保、套利 | ~5% |
| 币本位永续 | BTC | 无 | BTCUSD-PERP | 囤币党 | ~15% |
| 币本位交割 | BTC | 有 | BTCUSD-0329 | 机构对冲 | <5% |

## 五、现货 vs 衍生品的本质区别

| 核心维度 | 现货交易 | 衍生品（合约）交易 |
|---------|---------|----------------|
| 交易标的 | 真实资产（BTC / ETH） | 价格协议，不涉及实物 |
| 所有权 | 完全拥有，可提现 | 无，只持有仓位 |
| 结算方式 | 即时，T+0 | 平仓或到期时现金结算 |
| 资金效率 | 低，1:1 | 高，可达 1:125 |
| 做空能力 | 无（杠杆可实现） | 原生支持做空 |
| 最大亏损 | 本金归零，不负债 | 保证金归零（爆仓） |
| 适合人群 | 长期持有、价值投资 | 短线交易、对冲套利 |

以一笔完整的现货交易为例：**用 4000 USDT 限价买入 0.1 ETH，然后提现到硬件钱包**，追踪八大系统的协作过程。

### 6.2 阶段一：登录认证（约 1 秒）

**交易网关层：**
- 检查 IP 请求频率，防暴力破解
- 解密 HTTPS 传输内容，路由到用户权限中心

**用户权限中心：**
- 验证密码（bcrypt 哈希，数据库泄露也无法逆推）
- 检查账户状态（是否被风控冻结）
- 发送短信验证码（6 位，5 分钟有效）
- 颁发 JWT Token（有效期 24 小时），后续请求携带 Token，无需再查库

### 6.3 阶段二：充值（约 30 分钟，受制于区块链）

**链上充值流程：**

1. **资金中心**为用户生成专属充值地址（基于 HD 钱包路径派生，如 `m/44'/60'/0'/0/123456`）
2. 用户从外部钱包转账 4000 USDT 到该地址
3. 交易所区块链扫描程序每 10 秒检查一次新区块，监听 USDT 合约的 Transfer 事件
4. 发现入账交易后，等待 **12 个区块确认**（以太坊约 2~3 分钟，防止链重组回滚）
5. 风控系统查询链上地址画像（通过 Chainalysis 等工具），确认资金来源非黑名单地址、非混币器，自动审核通过
6. 数据库原子写入，账户余额更新，推送充值到账通知

**充值入账 SQL（简化）：**
```sql
BEGIN TRANSACTION;
  UPDATE user_fund_account
    SET usdt_balance = usdt_balance + 4000
    WHERE user_id = 'UID_123456';
  INSERT INTO deposit_records VALUES ('UID_123456', 4000, '0x1234...', 'SUCCESS', NOW());
COMMIT;
```

**资金账户 → 交易账户划转：**

充值后资金在"资金账户"，需划转至"交易账户"才能下单。两个账户在同一数据库内，通过原子事务实现，要么同时成功，要么整体回滚，不存在资金"凭空消失"的情况。

### 6.4 阶段三：下单与风控（约 100 毫秒）

柜台系统通过 Kafka 与撮合引擎解耦：即使撮合引擎短暂重启，消息不会丢失，订单不会遗漏。

### 6.5 阶段四：撮合成交（约 10 毫秒）

撮合引擎从 Kafka 消费订单消息，在**全内存订单簿**中进行匹配：

**当前订单簿（简化）：**
```
卖盘（Ask）：
  39990 USDT → 0.20 ETH
  39985 USDT → 0.10 ETH
  39980 USDT → 0.05 ETH  ← 最优卖价

小明买单：40000 USDT → 0.1 ETH
```

**撮合过程（价格优先）：**
- 第一轮：40000 ≥ 39980，与 0.05 ETH 成交，成交价 **39980 USDT**
- 第二轮：40000 ≥ 39985，与剩余 0.05 ETH 成交，成交价 **39985 USDT**
- 全部成交，加权平均价 **39982.5 USDT**

> 限价买单的成交价取**卖方报价**（而非买方挂单价），因此小明实际花费 3998.25 USDT，低于挂单的 4000 USDT，差额解冻退回。

### 6.6 阶段五：清算结算

撮合成功后，清算系统以**一个原子事务**完成多账户余额更新：

```sql
BEGIN TRANSACTION;
  -- 买方（小明）：扣 USDT，加 ETH，解冻冻结资金
  UPDATE trade_account SET
    eth_balance   = eth_balance + 0.1,
    usdt_frozen   = usdt_frozen - 4000,
    usdt_balance  = usdt_balance + 1.75   -- 退回未用金额
  WHERE user_id = 'UID_123456';

  -- 卖方 1（用户B）：加 USDT，扣 ETH
  UPDATE trade_account SET
    eth_balance  = eth_balance - 0.05,
    usdt_balance = usdt_balance + 1999
  WHERE user_id = 'UID_B';

  -- 卖方 2（用户C）：加 USDT，扣 ETH
  UPDATE trade_account SET
    eth_balance  = eth_balance - 0.05,
    usdt_balance = usdt_balance + 1999.25
  WHERE user_id = 'UID_C';

  -- 更新订单状态
  UPDATE orders SET status='FILLED', avg_price=39982.5 WHERE order_id='ORD_...';

  -- 写入成交记录
  INSERT INTO trade_records VALUES ('UID_123456', 0.1, 39982.5, 'BUY', NOW());
COMMIT;
```

任何一条语句失败，整个事务回滚，资金不会处于中间状态。

### 6.7 阶段六：行情推送（实时）

清算完成后，行情系统接收撮合引擎的成交数据：
- 更新最新成交价：39982.5 USDT
- 更新各周期 K 线（1m / 5m / 1h / 1d）的 OHLCV 数据
- 通过 **WebSocket** 广播给所有订阅该交易对的用户

小明 APP 实时收到持仓更新推送：ETH 余额 +0.1，成本价 39982.5 USDT。

### 6.8 阶段七：提现到钱包（约 10 分钟）

**风控审核：**
- 检查目标地址：非黑名单，格式正确
- 首次向该地址提现：需邮件 + 短信二次确认
- 检查提现限额：0.1 ETH < 单日限额 ✓

**资金处理：**
- 冻结用户账户中的 0.1 ETH
- 扣除网络 Gas 费（如 0.001 ETH），实际到账 0.099 ETH
- 将提现请求写入队列

**链上广播：**
- 从交易所**热钱包**发起链上转账
- 热钱包采用**多签方案**（如 2/3 签名），需多位授权人分别签名，防止单点失控
- 交易广播到以太坊网络，等待 12 个区块确认
- 确认完成后，更新提现记录状态为 SUCCESS，通知用户

```
小明硬件钱包收到 0.099 ETH ✓
```

## 七、系统设计核心原则

| 原则 | 实现方式 | 目标 |
|------|---------|------|
| 微服务架构 | 每个系统职责单一，独立部署 | 故障隔离，独立扩容 |
| 原子事务 | 关键资金操作在单个 DB 事务内完成 | 防止资金"半途消失"或"重复到账" |
| 异步解耦 | 柜台与撮合引擎通过 Kafka 通信 | 撮合引擎可独立扩容，系统重启不丢单 |
| 内存计算 | 撮合引擎订单簿全部在内存 | 毫秒级撮合，支持万级 TPS |
| 缓存加速 | Redis 缓存热点数据（用户订单、余额） | 降低数据库压力，提升查询速度 |
| 多层安全 | 登录（密码+SMS+JWT）、提现（二次验证+多签热钱包） | 纵深防御，单层突破不危及整体 |

## 八、总结

一笔"简单"的限价买单，实际经过了 **8 大系统、7 个处理阶段**：

| 阶段 | 耗时 | 关键系统 |
|------|------|---------|
| 登录认证 | ~1 秒 | 交易网关、用户权限中心 |
| 链上充值 | ~30 分钟 | 资金中心、区块链监控 |
| 账户划转 | ~1 秒 | 资金中心 |
| 下单风控 | ~100 毫秒 | 网关、风控、资金中心、柜台 |
| 撮合成交 | ~10 毫秒 | 撮合引擎 |
| 清算结算 | ~50 毫秒 | 清算系统 |
| 提现上链 | ~10 分钟 | 风控、资金中心、区块链广播 |

充值和提现的耗时主要由区块链确认时间决定，与交易所系统性能无关；而下单到成交的全链路，控制在 **100 毫秒**以内。
