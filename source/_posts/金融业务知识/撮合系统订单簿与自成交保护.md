> 本文侧重业务逻辑讲解，介绍撮合系统中订单簿的结构与运转机制，以及自成交保护的业务规则。

---

## 一、订单簿是什么？

**订单簿（Order Book）** 是撮合交易系统的核心，它实时记录市场上所有**尚未成交的限价挂单**，是当前市场买卖双方意愿的直接体现。

订单簿分为两侧：

```
      价格
        ↑
卖三  31,500  |  20 BTC   ← 卖方（Ask/Offer）
卖二  31,200  |  15 BTC     价格由低到高排列
卖一  31,000  |  30 BTC   ← 最低卖价（Best Ask）
────────────────────────── 买卖价差（Spread）
买一  30,900  |  50 BTC   ← 最高买价（Best Bid）
买二  30,700  |  40 BTC     价格由高到低排列
买三  30,500  |  25 BTC   ← 买方（Bid）
        ↓
```

- **买单队列（Bids）**：价格从高到低排列，出价越高越优先
- **卖单队列（Asks）**：价格从低到高排列，要价越低越优先
- **同一价格内**：按时间先后排列，先下单者优先成交（时间优先）
- **买卖价差（Spread）**：买一与卖一之间的差值，价差越小说明市场流动性越好

---

## 二、撮合的核心规则：价格优先，时间优先

撮合引擎从始至终只遵循一条规则：

```
同等条件下，出价最高的买单最优先；
同等条件下，要价最低的卖单最优先；
价格相同时，先下单的先成交。
```

一笔新订单进入系统后，撮合引擎会立即检查对手方订单簿，判断是否存在可成交的挂单。

---

## 三、撮合流程详解

### 3.1 限价单的撮合

限价单指定了一个可接受的成交价格：
- **买入限价单**：只接受 ≤ 限价的成交价
- **卖出限价单**：只接受 ≥ 限价的成交价

**流程：**
```
新限价订单进入
      ↓
检查对手方订单簿，是否存在满足价格条件的挂单？
      ├── 有 → 按价格优先、时间优先依次撮合
      │         完全成交 → 订单结束
      │         部分成交 → 剩余数量挂入订单簿等待
      └── 无 → 整单挂入订单簿等待
```

### 3.2 市价单的撮合

市价单不指定价格，要求以当前市场最优价格**立即成交**：

```
新市价订单进入
      ↓
直接从对手方订单簿的最优价格开始撮合
      ↓
一档不够 → 继续消耗下一档
      ↓
直到订单全部成交（或订单簿深度耗尽）
```

市价单会"吃穿"多个价格档位，产生**滑点**——实际平均成交价与下单时预期的价格存在偏差。

## 四、订单簿撮合案例

### 当前订单簿状态

| 方向 | 价格（USDT） | 数量（BTC） |
|------|------------|------------|
| 卖三 | 31,500     | 25         |
| 卖二 | 31,200     | 30         |
| **卖一** | **31,000** | **45**     |
| **买一** | **30,900** | **80**     |
| 买二 | 30,700     | 75         |
| 买三 | 30,500     | 60         |

---

### 案例一：单档位撮合

**新订单：** 市价买入 30 BTC

```
撮合过程：
① 以卖一价 31,000 USDT 成交 30 BTC

结果：
  成交：30 BTC @ 31,000 USDT
  卖一剩余：45 - 30 = 15 BTC @ 31,000 USDT
```

**订单簿更新后：**

| 方向 | 价格 | 数量 |
|------|------|------|
| 卖三 | 31,500 | 25 |
| 卖二 | 31,200 | 30 |
| **卖一** | **31,000** | **15**（减少了 30）|
| 买一 | 30,900 | 80 |

---

### 案例二：穿越多档位撮合（产生滑点）

**新订单：** 市价买入 100 BTC

```
撮合过程：
① 以卖一 31,000 USDT 成交 45 BTC → 卖一完全消耗，剩余 55 BTC 待成交
② 以卖二 31,200 USDT 成交 30 BTC → 卖二完全消耗，剩余 25 BTC 待成交
③ 以卖三 31,500 USDT 成交 25 BTC → 卖三完全消耗，订单全部成交

成交明细：
  45 BTC @ 31,000 USDT = 1,395,000 USDT
  30 BTC @ 31,200 USDT =   936,000 USDT
  25 BTC @ 31,500 USDT =   787,500 USDT

总成交额：3,118,500 USDT
平均成交价：3,118,500 / 100 = 31,185 USDT

滑点 = 31,185 - 31,000 = 185 USDT/BTC（相对卖一价）
```

**订单簿更新后：**

| 方向 | 价格 | 数量 |
|------|------|------|
| （原卖一/二/三全部被吃空） | | |
| **新卖一** | **31,800**（下一档） | ... |
| 买一 | 30,900 | 80 |

这就是**"吃深度"**——大额市价单穿越多个价格档位，买卖价差骤然扩大，价格冲击显著。

---

### 案例三：限价买单与挂单撮合

**新订单：** 限价买入 50 BTC @ 31,000 USDT

```
检查卖单队列，卖一为 31,000 USDT（满足 买入价 ≥ 卖出价 的条件）

撮合：以 31,000 USDT 成交 45 BTC（卖一全部）
剩余 5 BTC 未成交 → 以 31,000 USDT 挂入买单队列等待
```

## 五、市场深度的业务意义

**市场深度（Market Depth）** 是指在最优买卖价之外，各价格档位上堆积的挂单量。

```
深度厚（每档挂单多）
  → 大额订单对价格冲击小
  → 市场流动性好
  → 滑点小

深度薄（每档挂单少）
  → 大额订单穿越多个档位
  → 市场流动性差
  → 滑点大，价格波动剧烈
```

这也是机构交易者选择**冰山委托**或**VWAP/TWAP 算法**的原因——避免一次性大额市价单"砸穿"订单簿，造成过大的市场冲击成本。

## 六、自成交保护（Self-Trade Prevention）

### 6.1 什么是自成交？

**自成交**是指同一个账户（或同一实际控制人下的多个账户）的买单与卖单相互成交。

常见触发场景：
- 算法策略在两个子账户上同时挂了方向相反的订单，恰好被撮合引擎匹配
- 做市商在双向挂单时，因市价波动导致自己的买卖单相遇
- 手动下单时没有注意到已有存量挂单，重复操作方向相反的订单

### 6.2 自成交的危害

| 危害 | 说明 |
|------|------|
| **虚假成交量** | 自成交会产生真实记录但无实质意义的成交数据，误导其他市场参与者 |
| **价格操纵嫌疑** | 通过反复自成交可以人为制造某价格区间的"活跃"假象 |
| **无效手续费** | 每次成交都会产生手续费，自成交等于白白支付了两次费用 |
| **监管风险** | 主流交易所和监管机构均将自成交列为需要防范的异常交易行为 |

### 6.3 检测维度

不同交易所的自成交检测范围有所差异：

| 检测维度 | 说明 |
|---------|------|
| **同一账户内** | 最基础的检测，同一 UID 下买卖单互撮 |
| **同一 API Key 下** | 同一密钥管理的多个策略之间 |
| **母子账户之间** | 机构账户下不同子账户间的订单 |
| **关联账户** | 受同一实际控制人控制的多个账户（监管层面） |

---

## 七、三种自成交保护策略

当撮合引擎检测到即将发生自成交时，会在实际撮合**之前**介入，根据预设策略决定如何处理。

### 策略一：CancelTaker（取消新订单）

**处理方式：** 取消新进入的订单（Taker），保留订单簿中已有的挂单（Maker）。

```
场景：
  账户 A 在买单队列挂有 50 BTC @ 30,900（Maker）
  账户 A 又提交了一笔市价卖单 50 BTC（Taker）

检测：新订单与自己的挂单即将成交 → 自成交风险！

处理（CancelTaker）：
  ✗ 取消市价卖单（新订单）
  ✓ 保留 30,900 的买单（继续在订单簿中等待）
```

**适用场景：** 希望保持原有挂单策略不变，防止新订单意外干扰。

---

### 策略二：CancelMaker（取消存量挂单）

**处理方式：** 取消订单簿中已有的挂单（Maker），让新订单（Taker）继续尝试与市场上**其他人**的订单成交。

```
场景：
  账户 A 在买单队列挂有 50 BTC @ 30,900（Maker）
  账户 A 又提交了一笔市价卖单 50 BTC（Taker）

检测：即将自成交 → 触发保护！

处理（CancelMaker）：
  ✗ 取消 30,900 的挂单（Maker）
  ✓ 市价卖单继续寻找下一个可成交的对手方（买二、买三……）
```

**适用场景：** 希望新订单能快速成交，原有挂单可以牺牲。

---

### 策略三：CancelBoth（双向取消）

**处理方式：** 同时取消新订单（Taker）和对应的存量挂单（Maker），双方均不成交。

```
场景：
  账户 A 在买单队列挂有 50 BTC @ 30,900（Maker）
  账户 A 又提交了一笔市价卖单 50 BTC（Taker）

检测：即将自成交 → 触发保护！

处理（CancelBoth）：
  ✗ 取消市价卖单（Taker）
  ✗ 取消 30,900 的挂单（Maker）
  → 两笔订单均从市场中消失
```

**适用场景：** 对自成交零容忍的严格交易环境。

---

### 三种策略对比

| 策略 | 取消对象 | 保留对象 | 适用场景 |
|------|---------|---------|---------|
| **CancelTaker** | 新进入的订单 | 存量挂单 | 保护原有策略，阻止意外干扰 |
| **CancelMaker** | 存量挂单 | 新进入的订单 | 新订单优先，快速成交 |
| **CancelBoth** | 两者均取消 | 无 | 严格监管，零容忍自成交 |

---

## 八、主流交易所的自成交保护规范

| 交易所 | 默认策略 | 检测范围 | 特殊规定 |
|--------|---------|---------|---------|
| **Binance** | CancelTaker | API Key + UID | 合约与现货独立检测 |
| **OKX** | 可配置 | 账户 + 子账户 | 支持策略自定义 |
| **CME（传统期货）** | — | 账户组 + IP + 设备 | 允许大宗交易自成交 |
| **上交所** | 多种 | 客户代码 + 营业部 | 科创板执行更严格 |
| **NASDAQ** | CancelMaker | MPID 标识 | 做市商有豁免条款 |

## 九、整体业务流程总结

```
用户提交订单
      ↓
┌─────────────────────────────┐
│     自成交保护检测（前置）      │
│  检查是否与自己的挂单即将撮合   │
│  触发 → CancelTaker/Maker/Both│
└─────────────┬───────────────┘
              ↓（无自成交风险）
┌─────────────────────────────┐
│         撮合引擎             │
│  价格优先：买方出价高者先成交   │
│  时间优先：同价格先下单者先成交 │
└─────────────┬───────────────┘
              ↓
      ┌───────┴───────┐
   有匹配的对手方      无匹配的对手方
      ↓                    ↓
  执行撮合              挂入订单簿
  （可能多档位）          等待撮合
      ↓
  生成成交记录
  更新订单簿深度
  推送行情数据
```

撮合系统的核心业务逻辑并不复杂，但每一个细节——从价格优先的排序规则，到自成交保护的触发时机——都直接影响着市场的公平性和用户的交易体验。理解这些规则，能够帮助交易者更合理地设计下单策略，避免不必要的损失。
