本方案适合对 **一致性、可用性、低延迟** 有较高要求的有状态服务系统
# 1.整体架构概述
## 1.1.核心设计目标
- 高可用：单节点故障不影响服务，RTO（恢复时间目标）秒级
- 强一致：主从节点内存状态完全一致，可相互接管
- 低延迟：核心链路无锁化，避免分布式事务
- 可运维：支持计划内主动切换，不依赖人工干预完成故障恢复

## 1.2.适用场景
- **有状态内存引擎**：核心状态全量加载在内存中（如撮合引擎、账户引擎、风控引擎）
- **事件驱动系统**：通过系统队列驱动状态变更
- **金融级一致性要求**：不能接受主从不一致的任何时间窗口

# 2.主从架构设计
## 2.1.架构模型选择
本方案采用 **Active-Active 双节点主从模型**，而非 Active-Passive

| 特性 | Active-Passive | Active-Active |
| --- | --- | --- |
| 从节点状态 | 冷备，不处理数据 | 热备，实时跟随主节点 |
| 切换时间 | 分钟级（需要数据追赶） | 秒级（状态已同步） |
| 资源利用率 | 浪费 50% 计算资源 | 从节点承担快照，补偿等工作 |
| 一致性验证 | 仅切换后才发现偏差 | 实时指纹校验，问题立即暴露 |

## 2.2.节点职责分工
**主节点（Leader）职责**
- 消费 Kafka 消息并执行状态变更
- 每批处理完后向 Redis 发布版本号和状态指纹
- 对外提供读写服务

**从节点（Follower）职责**
- 消费相同 kafka 消息但受主节点版本控制（永不超过主节点）
- 执行与主节点星通的状态变更逻辑（独立计算，非同步复制）
- 负责定期写入状态快照（降低主节点 I/O 压力）
- 负责向 kafka 消息发送失败的补偿重发
- 向 Redis 周期性写入存活心跳

## 2.3.分组（Group）隔离
对于高吞吐场景，按照 **业务维度** 进行水平分组扩展
```
Group 0：主节点A + 从节点B（处理用户 ID % 2 == 0）的数据
Group 1：主节点C + 从节点D（处理用户 ID % 2 == 1）的数据
```
每个 Group 独立选主，独立维护内存状态，互不影响

# 3.Leader 选举机制
## 3.1.选举方案：Apache Curator LeaderLatch
基于 zookeeper 的 `LeaderLatch`实现分布式选主，这是 CAP 中选择 CP 的典型实现
```
Zookeeper Znode 结构：
/app/{group}/leader
    |-- latch-00001（节点A，当前持有锁，为 Leader）
    |-- latch-00002（节点B，监听节点A，为 Follower）
```

**选举流程**
```
节点启动
    ↓
向 ZK /app/{group}/leader/ 创建临时顺序节点
    ↓
检查自己是否序号最小的节点
    |—— 是 → 成为 leader，回调 isLeader()
    |__ 否 → 监听前一个节点，回调 notLeader()
                    ↓
            前序节点删除（宕机或者主动释放）
                    ↓
            当前节点成为 Leader
```
举个例子，为什么是序号最小，如果选最大会发生什么？
```
场景：3个节点同时参与选举

节点A 启动 → 创建 /app/leader/node-0000000001  
节点B 启动 → 创建 /app/leader/node-0000000002    
节点C 启动 → 创建 /app/leader/node-0000000003

ZK 目录结构：  
/app/leader/  
    ├── node-0000000001  ← 节点A  
    ├── node-0000000002  ← 节点B  
    └── node-0000000003  ← 节点C（序号最大） 

节点A 创建了 node-001  
节点B 创建了 node-002  
  
此时 节点B 是最大 → B 成为 Leader ✓  
  
但是！节点C 突然加入创建了 node-003  
→ C 变成最大 → C 也认为自己是 Leader ✗  
  
出现两个 Leader！！（脑裂）  
```
**为什么选最小最安全：序号是 ZK 单调递增分配的，node-001 一旦创建，永远是最小，除非 node-001 被删除，否则不会变化。**

其次，这种"监听前一个节点"而不是"所有节点都监听最小节点"的设计，还能避免"羊群效应"（Herd Effect），如果所有节点都监听 node-001，node-001 删除时会触发大量通知，造成 ZK 压力激增。

## 3.2.ClusterService 设计
所有模块通过统一的 `ClusterService` 获取当前节点角色，避免直接依赖 ZK
```java
/**
 * 集群节点角色服务，全局单例
 */
public class ClusterService {

    // volatile 保证多线程可见性，ZK 回调线程写，业务线程读
    private volatile boolean leader = false;

    public boolean isLeader() {
        return leader;
    }

    public void setLeader(boolean leader) {
        this.leader = leader;
        // 发布角色变更事件，通知下游模块（快照策略、补偿任务等）
        applicationEventPublisher.publishEvent(new LeaderChangeEvent(leader));
    }
}
```

# 4.主从一致性保证
## 4.1.核心思路：Kafka 数据对齐 + 版本锚点 + 指纹校验
```
主节点处理消息 offset=1000
    ↓
计算本批次所有输出消息的 MD5 fingerprint
    ↓
写入 Redis: KEY=master_version_{group}, VALUE={offset:1000, fingerprint:"abc123"}
    ↓
从节点后台任务每 10ms 拉取 Redis 版本到内存
    ↓
从节点处理消息时：
    if (myOffset > masterVersion) → 等待 500ms 重试（不超前主节点）
    if (myOffset == masterVersion) → 计算自己的 fingerprint 并与 Redis 中比较
        ├── 相等 → 状态一致，继续处理
        └── 不等 → 状态已发散，立即停机并告警
```

## 4.2.版本号设计
版本号直接使用 **Kafka Offset**，天然具备单调递增性，无需额外维护序列。
```java
/**
 * 主节点版本变更监听器，在每批消息处理完后触发
 * @author Reln Ding
 */
public class MasterVersionChangeListener {

    public void onChange(long kafkaOffset, List<OutputMessage> outputMessages) {
        String fingerprint = fingerprintFactory.buildFingerprint(outputMessages);
        masterVersionRedisClient.set(group, kafkaOffset, fingerprint);
    }
}
```

## 4.3.指纹（Fingerprint）计算
指纹的计算对象 **本批次所有输出消息** （发往 Kafka 的消息），而非内存状态本身
- 优点：不需要对全量内存状态做哈希（开销极大），只需要增量输出做哈希
- 原理：相同输入 + 相同处理逻辑 -> 相同输出，因此输出一致性等价于状态一致性

```java
public String buildFingerprint(List<OutputMessage> messages) {  
    // 对所有输出消息按固定顺序排序后做 MD5  
    return DigestUtils.md5Hex(  
        messages.stream()  
            .sorted(Comparator.comparing(OutputMessage::getKey))  
            .map(OutputMessage::toBytes)  
            .collect(joining())  
    );  
}
```

# 5.故障检测与自动切换
## 5.1.从节点存活检测
![从节点存活检测](/images/HA/从节点存活检测.png)
**TTL 设计建议：**TTL 应该设置为心跳间隔的 **20-24** 倍，留足网络抖动个 GC 暂停的容忍空间

## 5.2.主节点故障处理
![主节点故障处理](/images/HA/主节点故障处理.png)

**RTO 分析**
- ZK session 超时：30s（可调低到 10s，但需平衡网络抖动的风险）
- 从节点感知并接管：<1s
- **总 RTO：约 10-30s**

## 5.3.脑裂（Split-Brain）防护
Zookeeper 本身通过 Quorum 机制防止脑裂：只有能联系半数以上 ZK 节点的应用节点才能持有 Leader

但需要额外注意一下情况：
| 场景 | 防护措施 |
| --- | --- |
| ZK 链接短暂中断 | `ExponentialBackoffRetry`重连，不立即释放 Leader |
| ZK 链接长时间中断 | Session 超时后自动释放临时节点，出发重新选举 |
| 主节点进程未宕机但 ZK 失联 | 主节点应监听 `notLeader()`回调，停止处理消息，防止双主写入 |
| 网络分区 | ZK 多数派原则保证只有一侧可以成为 Leader() |

## 5.4.主节点异常自停机
当主节点内部发生无法恢复的异常（如状态计算错误、状态依赖不可用），应主动停机而非带病运行
```java
/**  
 * Disruptor 主线程异常处理器  
 * @author Reln Ding  
 */  
public class MainThreadExceptionHandler implements ExceptionHandler<RingBufferEvent> {  
  
    @Override  
    public void handleEventException(Throwable ex, long sequence, RingBufferEvent event) {  
        // 1. 记录详细错误日志  
        log.error("Fatal error in main processing thread", ex);  
  
        // 2. 发送紧急告警  
        alertService.sendCriticalAlert(WarnEnum.FATAL_EXCEPTION, ex.getMessage());  
  
        // 3. 主动退出 JVM，触发 K8s/容器重启  
        // 注意：必须是 System.exit 而非 Thread.stop，确保 JVM shutdown hook 执行  
        serverManager.tryShutdown();  
    }  
}  
```

# 6.状态快照与故障恢复
## 6.1.快照的必要性
系统每次重启都从最新的快照恢复，然后从快照对应的 Kafka offset 开始重放消息。如果没有快照：
- 每次重启都需要从最早的 Kafka 消息进行回放（可能数年）
- 重放时间可能长达数小时，严重影响 RTO

## 6.2.快照创建流程
```
触发快照（定时 or 手动触发）
        ↓
暂停 Disruptor 消费（或者使用 Copy-on-Write 快照）
        ↓
遍历所有内存数据类型（用户账户、订单列表、配置等）
        ↓
序列化为字节流（推肩 ProtoBuf、SBE、Kryo，避免 Java 序列原生化）
        ↓
计算 CRC32 校验和
        ↓
写入本地文件系统（异步写，通过 Disruptor）
        ↓
写入 DB 记录快照元数据（版本、路径、状态、CRC32）
```

### 6.2.1.暂停 Disruptor 消费 vs Copy-on-Write
暂停 Disruptor 消费
```
正常状态：  
Kafka → Disruptor → 处理消息 → 修改内存数据  
  
快照时：  
Kafka → Disruptor → ⏸️ 暂停消费  
                         ↓  
                    此时内存数据静止不变  
                         ↓  
                    安全地做快照  
                         ↓  
                    快照完成 → ▶️ 恢复消费  
  
问题：快照期间系统停止处理，有延迟！ 
```

Copy-on-Write
```
快照触发时：  
内存数据 → 复制一份副本（Copy）  
              ↓           ↓  
         副本做快照    原数据继续处理新消息  
         （慢慢写）    （不受影响）  
  
优点：系统不停机，边快照边处理  
缺点：需要额外内存存储副本 
```

**总结**

- 暂停消费 = 保证快照时数据不变，简单但有停顿
- Copy-on-Write = 复制副本做快照，不停机但耗内存
### 6.2.2.为什么计算 CRC32 校验和
场景：快照文件写入磁盘过程中
```
正常写入：  
[内存数据] → 序列化 → [完整文件 ✅]  
  
异常情况：  
[内存数据] → 序列化 → 写到一半 → 机器宕机！  
                      [残缺文件 ❌]  
  
恢复时加载残缺文件 → 数据错乱 → 💥 系统异常
```

有了 CRC32：
```
写入时：  
数据 → 计算CRC32=12345 → 一起写入文件  
  
恢复时：  
读取文件 → 重新计算CRC32=?  
              ↓  
    ?=12345 ✅ 文件完整，可以加载  
    ?≠12345 ❌ 文件损坏，拒绝加载  
                    ↓  
              回滚到上一个快照  
```
**总结**

CRC32 = 防止快照文件损坏导致恢复时数据错乱，类似文件的"防伪码"

## 6.3.快照责任分配策略
| 场景 | 快照执行节点 | 原因 |
| --- | --- | --- |
| 正常运行（双节点健康） | 从节点不可用，主节点兜底 |
| 从节点宕机 | 主节点 | 从节点不可用，主节点兜底 |
| 特殊恢复模式（配置项） | 强制主节点 | 需要主节点状态的权威快照 |

```java
public boolean needSnapshot() {  
    if (config.isForceLeader()) {  
        return clusterService.isLeader();  
    }  
    if (clusterService.isLeader()) {  
        // 主节点：仅在从节点宕机时才做快照  
        return !followerService.isFollowerAlive();  
    } else {  
        // 从节点：始终负责快照  
        return true;  
    }  
}  
```

## 6.4.快照保留策略
- 短期快照：保留最近 N 份（如 N=6，每5分钟一份，覆盖最近30分钟）
- 长期快照：从短期快照中每隔 T 时间晋升一份（如每一小时一份，保留6份）

删除旧快照：
1. 查询 DB 中同 group_id 的快照，按版本倒序排列
2. 保留前 N 条，删除其余的 DB 记录和本地文件

## 6.5.故障恢复
1. RecoveryService.recover
2. 从 DB 查询该 group 最新 COMPLETED 状态的快照元数据
3. 读取本地快照文件 验证 CRC32
4. 检查 data_types 字段 确认所有必需数据类型都存在
5. 逐类型调用 SnapshotActor.recover 账户余额、订单列表、风控参数、符号配置...
6. 重置 Kafka Consumer Offset 到 snapshot.version
7. 启动 Disruptor 从该 offset 开始重放 Kafka 消息
8. 重放完毕 向 ZooKeeper 注册 参与 Leader 选举

**关键设计：先恢复状态，再参与选举**，避免状态未就绪的节点成为 Leader

## 6.6.Kafka 和 Offset 的配合使用
Kafka 不是数据库，它按"保留策略"存储消息：  
  
按时间保留：retention.ms = 7天 (默认)  
按大小保留：retention.bytes = 1GB

```
时间线：  
Day1  Day2  Day3  Day4  Day5  Day6  Day7  Day8  
|-----|-----|-----|-----|-----|-----|-----|  
offset=100                          offset=10000  
```

Day1的消息到期 → 自动删除！  
此时 offset=100 的消息已经不存在了  

**因此，这里就是快照保存策略存在的原因:快照不能太旧！**

快照保留时间  必须 << Kafka 保留时间  
```
Kafka 保留: 7天  
快照保留:   30分钟 (短期) / 6小时 (长期)  
  
恢复时：  
最新快照 offset = 6小时前  
Kafka 还保留着 7天内的消息
```

# 7.消息队列设计
## 7.1.生产者配置
```yaml
kafka:
  producer:
    acks: all                          # 所有副本确认，最强持久性
    retries: 2147483647                # 无限重试
    max-in-flight-requests-per-connection: 1  # 严格有序，禁止乱序
    enable-idempotence: true           # 幂等生产，防重复
    compression-type: lz4              # 压缩降低网络带宽
    linger-ms: 2                       # 微小延迟换更大吞吐
    batch-size: 524288                 # 512KB 批大小
    delivery-timeout-ms: 1200000      # 20 分钟超时（配合无限重试）
```

## 7.2.消费者配置
```yaml
kafka:
  consumer:
    enable-auto-commit: false          # 手动提交 offset，精确控制
    auto-offset-reset: earliest        # 重启后从已知位置重放，而非丢弃
    max-poll-records: 1000             # 每批最多消费条数
    fetch-max-wait-ms: 1              # 极低延迟，有消息立即拉取
    session-timeout-ms: 30000
    heartbeat-interval-ms: 3000
```

## 7.3.Kafka 发送失败补偿机制
网络抖动可能导致 Kafka 发送失败，不能直接丢弃：
```
消息发送失败
    ↓
写入 DB 表 kafka_send_failed_data（包含消息内容、topic、partition、创建时间）
    ↓
定时任务（由从节点执行，每 N 秒运行一次）
    ↓
查询 kafka_send_failed_data 表中未处理的记录
    ↓
重新发送到 Kafka
    ↓
发送成功 → 删除 DB 记录
```

**为什么由从节点执行补偿？**
- 从节点负载相对较低
- 主节点专注于核心消息处理，降低主节点压力
- 即使从节点宕机，主节点也能通过 `isLeader()` 判断后自行接管补偿任务

# 8.存储层设计
## 8.1.分层存储设计
```
内存层（实时）
  └── 主/从节点全量内存状态（HashMap、有序集合等）
      响应时间：微秒级

快照层（准实时）
  └── 本地文件系统的状态快照（每 5-30 分钟）
      用途：快速故障恢复

持久化层（最终一致）
  └── Kafka → Store 服务 → MySQL/MariaDB
      用途：数据查询、审计、报表
```

## 8.2.数据库分组隔离
每个业务 Group 使用独立数据库，防止相互影响：

```
数据库: app_{group_id}
  ├── snapshot_meta          -- 快照元数据
  ├── kafka_send_failed_data -- Kafka 发送失败补偿
  └── {business_tables}      -- 业务数据表
```

## 8.3.连接池配置建议
```yaml
datasource:
  hikari:
    connection-timeout: 2000      # 2s 获取连接超时
    maximum-pool-size: 50         # 最大连接数（根据 DB 服务器配置调整）
    minimum-idle: 10              # 最小空闲连接
    transaction-isolation: TRANSACTION_READ_COMMITTED  # 读已提交，避免幻读影响性能
    keepalive-time: 30000         # 防止连接被防火墙断开
```

## 8.4.分表方案
对于高写入量的补偿表，使用 ShardingSphere 进行水平分表：

```yaml
shardingsphere:
  rules:
    sharding:
      tables:
        kafka_send_failed_data:
          actual-data-nodes: ds.kafka_send_failed_data_$->{0..7}
          table-strategy:
            standard:
              sharding-column: user_id
              sharding-algorithm-name: mod8
```

### 8.4.1.ShardingSphere 水平分表方案
水平分表：把一张大表的数据，按某个规则拆分到多张结构相同的表中
```
orders 表 (1亿条数据)  
        ↓ 分表  
orders_0  orders_1  orders_2  orders_3  
(2500万)  (2500万)  (2500万)  (2500万)  
```

**常用分片策略**
- Hash 取模分片
```yaml
// 配置  
sharding:  
  tables:  
    orders:  
      actual-data-nodes: ds.orders_$->{0..3}  
      table-strategy:  
        standard:  
          sharding-column: order_id  
          sharding-algorithm-name: orders-inline  
  
  sharding-algorithms:  
    orders-inline:  
      type: INLINE  
      props:  
        algorithm-expression: orders_$->{order_id % 4}  
  
// 效果：  
order_id=1000 → 1000 % 4 = 0 → orders_0  
order_id=1001 → 1001 % 4 = 1 → orders_1  
order_id=1002 → 1002 % 4 = 2 → orders_2  
order_id=1003 → 1003 % 4 = 3 → orders_3  
```

- 按时间范围分片
```yaml
// 按月分表  
sharding-algorithms:  
  orders-by-month:  
    type: INTERVAL  
    props:  
      datetime-pattern: yyyy-MM-dd  
      datetime-lower: 2024-01-01  
      datetime-upper: 2024-12-31  
      sharding-suffix-pattern: yyyyMM  
      datetime-interval-amount: 1  
      datetime-interval-unit: MONTHS  
  
// 效果：  
2024-01-15 的订单 → orders_202401  
2024-02-15 的订单 → orders_202402  
2024-03-15 的订单 → orders_202403  
```

- 复合分片（Hash + 时间）
```yaml
// 同时按 user_id 和 create_time 分片  
table-strategy:  
  complex:  
    sharding-columns: user_id, create_time  
    sharding-algorithm-name: orders-complex  
  
// 效果：  
user_id=100, 2024-01 → orders_202401_0  
user_id=101, 2024-02 → orders_202402_1  
```

**选择分片键的原则**
- 数据均匀分布：避免热点，Hash 取模最均匀
- 查询必带分片键：否则全分片扫描
- 不可变字段：user_id、order_id 比 status 更合适
- 高基数字段：值尽量多，避免集中在某几个分片
